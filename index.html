The problem

Why multi-site reporting breaks

Nobody buys a dashboard. They buy the ability to rank their sites and trust the order.

When you operate one site, reporting is arithmetic. When you operate fifteen, it becomes a definitions problem. Each site has recorded things slightly differently, for reasons that made sense locally. Someone builds a roll-up. It doesn't reconcile to the sum of its parts. And from then on every performance conversation starts with an argument about the number rather than a decision about the site.

The cause is almost never the reporting tool. It's that nobody owns the layer where a metric is defined once and applied everywhere — what dimensional modelling calls conformed dimensions, and what your operations team experiences as "why does Site 7 look worse than it is?"

My work is to build that layer and make it accountable. Data lands in a governed pipeline. Facts and dimensions are modelled once and conformed across sites, so financial, operational and benchmarking figures filter together instead of contradicting each other. Definitions live in one semantic model rather than in each site's spreadsheet. Access is controlled at the row, so a site manager sees their site without you emailing fifteen different files.

Roll-ups that don't reconcile The portfolio total doesn't equal the sum of the sites, and nobody can say which one is wrong.
Unfair comparisons Sites of different sizes ranked on raw totals, so the biggest always looks best and the ranking tells you nothing.
Slow site onboarding A new location takes weeks to appear in reporting because someone has to hand-wire it in.
Fifteen versions of one file Access managed by emailing different workbooks to different managers, with no way to know who has what.

Engagement model

How I work

Phased, with sign-off at each stage. You should never be several months into a build before you see something you can use.

1

Assess

We trace the chain from each site's source system to the decision it feeds, and find where it breaks — contested definitions, mismatched grain, manual steps, unowned handoffs. Scope and risks get defined before anything is built.

2

Build in phases

Pipeline, then conformed model, then reporting, delivered in Agile milestones with sign-off at each one. Figures are reconciled to source as we go, so trust is established during the build rather than argued about after it.

3

Govern and hand over

Row-level security by site, deployment pipelines, version control and documentation, plus training. The measure of a good handover is that your team can add a site without me.

Continuity

"What happens if you're unavailable?"

It's the right question to ask any independent consultant, and most can't answer it well. Here's mine.

Your reporting is not trapped in my file. I develop in the .pbip project format with Git version control, which stores report and model metadata as readable text. That gives you complete change history, visible diffs on every modification, code review, and the ability to roll back — the things application code has had for decades and most BI work still doesn't.

The architecture is documented, not remembered. Metadata documentation, defined grain, and tie-out reports that reconcile the model against your source system. Another competent Fabric practitioner can read it and continue.

Promotion paths already exist. Deployment pipelines across development, test and production mean changes follow a defined route rather than depending on me being at my desk.

Handover is a deliverable, not a goodbye. Training is part of the engagement, and the standard I hold myself to is that your team can onboard a new site without calling me.
